# Design: Manually Run Scheduled Agent Workflows

Approved by the user on 2026-09-20 ("apprioved"). Build phases may proceed through implementation, review, and QA without further phase approvals.

## Approach
Extend the existing kind `46020` command, Postgres workflow records, relay-only `46008` tasks, and hosted-agent settings with a durable admission and execution protocol. Postgres owns quotas and lifecycle; the ACP harness owns supervised execution and stopping evidence. Reject browser-only throttling because CLI requests, reconnects, and relay restarts bypass it. This follows VISION.md's relay-enforced community boundary and VISION_REMOTE_AGENTS.md's relay control plane; a stopped process is evidence, absence of presence is not. Source takes precedence over stale vision text claiming approval suspension remains unimplemented.

## Stack & Dependencies
Reuse Rust/Tokio, SQLx/Postgres transactions, existing Nostr signing/NIP-98, chrono/cron, safe nix process-group termination, React Query, existing web/Tauri workflow APIs, Lucide icons, and Playwright. No new third-party dependencies. Add narrowly scoped workflow protocol/auth modules rather than another service or scheduler. UTC is the current scheduler timezone; interval schedules show their duration and an unknown next occurrence unless an actual scheduler anchor is available; durable occurrence buckets alone are not that anchor.

## Data Model / Interfaces
- **Supported manual profile:** enabled, channel-scoped scheduled definitions comprising only static `send_message` agent tasks; one or two `(step_id, target_pubkey)` pairs in total, fixed destinations, no conditions/templates in targeting, webhook, approval, delay, DM, other side-effect steps, recursive automation, or agent delegation. Validate before charging. A one-task brief can retry once; a two-task workflow gets one attempt per task. Unsupported definitions remain visible with a reason. Ordinary scheduled execution retains its existing action capabilities and does not consume manual quotas. Existing nonconforming manual commands now fail closed with `unsupported_manual_profile` rather than bypass safeguards; this is an intentional compatibility restriction.
- **Stable binding:** add optional `agent_targets: [hex_pubkey]` to `SendMessage`, validated against immutable managed-agent ownership and each destination's current admission rules. Store `workflow_agent_bindings(community_id, workflow_id, definition_hash, step_id, agent_pubkey, destination_channel, provenance)` with composite FK and unique target key. Once bound, dispatch/discovery use pubkeys, never re-resolve a renamed display name. On legacy definitions, bootstrap only from unambiguous persisted relay-signed `46008` evidence provably matching the current definition hash/step/destination (legacy evidence without that proof is insufficient), or an owner-signed definition update carrying explicit targets; otherwise show `association_unresolved`. Invalidate bindings on definition changes. Suite's four seeded schedules must be republished with explicit pubkeys by its existing owner-authenticated provisioner; names/prompts remain presentation.
- **Durable records:** extend `workflow_runs` with `origin(manual|scheduled|event)`, requester, accepted_at, deadline_at, definition_hash/snapshot, execution_state(`queued|running|completed|failed|timed_out|stalled`), dispatch_complete, safe_error_code, and revision. Preserve existing dispatch trace/status separately; old runs without acknowledgments have actual outcome `unknown`. Add `workflow_manual_requests(community_id, request_event_id PK-with-community, workflow_id, requester, decision, run_id?, reason?, created_at)`; accepted requests charge once, even on failure. Rejected exact retries return their recorded decision. Store no prompts in request receipts.
- Add `workflow_run_tasks(community_id, run_id, task_id, step_id, agent_pubkey, channel_id, task_event_id, state, result_event_id?, runner_instance?, attempt_count)` and `workflow_run_attempts(..., ordinal, task_id, grant_id UNIQUE, instance_id, claimed_at, deadline_at, stopped_at?, outcome?)`. All IDs and foreign keys include community. Enforce positive ordinals with a unique `(community_id, run_id, ordinal)` key and a transaction-checked ceiling of two only for manual runs. Two ordinals belong to the entire manual run. Scheduled tasks use the same completion evidence without the manual two-attempt/day limits.
- Add `workflow_run_outbox(community_id, id, run_id, event_id UNIQUE, signed_event, delivered_at?)`, `workflow_execution_capabilities(community_id, agent_pubkey, instance_id, protocol_version, expires_at)`, and `workflow_run_credentials(community_id, ephemeral_pubkey, run_id, agent_pubkey, attempt_ordinal, expires_at, revoked_at?)`. Only public credential keys enter relay storage. Add a per-community admission mutex row; task/active indexes are tenant-scoped. Scheduled claims gain `outcome=started|skipped_active` and optional run_id; no synthetic completed run for a skipped occurrence.
- **Atomic admission:** lock community mutex then workflow row in one DB transaction, using DB time. Recheck exact community-owner identity for hosted/manual-agent controls AND existing workflow-owner equality, active lifecycle, owner/channel permissions, target permissions, definition revision, capability freshness, and eligibility. Check all active workflow runs (scheduled or manual), manual active targets, and community counters together. Limits: cooldown 15 minutes since acceptance; three accepted runs/workflow and ten/community in `(now-24h, now]`; one active manual run/target and two/community. `stalled` is active. Write command event, request decision, run/tasks, and initial outbox in the same transaction; the existing command code's separate pool write is not sufficient atomicity. Reject immediately; never defer a denied request. Authority changes are rechecked at execution claims, without relying on stale caches.
- **Scheduler collision:** its deterministic occurrence claim and run admission take the same community/workflow locks. A colliding active manual run writes `skipped_active`; advance the existing occurrence anchor exactly as a consumed slot, without a run, catch-up, or shifting cadence. A scheduled run already queued/executing blocks manual admission until its actual targeted tasks finish. Existing pre-upgrade in-flight tasks are conservatively `unknown/stalled` until stopped evidence or a controlled runner restart verifies they ended; never use dispatch completion to clear them.
- **Wire commands:** retain `46020` with `d=workflow_id`; settings supplies `expected_definition_hash` as a reserved command field, never a template variable. Relay acceptance returns existing command receipt plus `run_id` and `revision`; rejections carry stable codes, `remaining_workflow`, `remaining_community`, `next_eligible_at?`, `server_now`. Time eligibility is the max of cooldown and rolling-window expiry; concurrency blocks have unknown eligibility time. Remaining allowance is projected from accepted rows, never client counters.
- Reserve `46040` for agent-signed control (`capability`, `claim`, `started`, `finished`, `stopped`); `46041` for relay-only grant/cancel decisions; `46042` for relay-only run status invalidation. Add these to canonical kind definitions, delivery, query visibility, and SDK builders. Envelopes use version 1, community, run/task/grant IDs, monotonic revision, exact `p` target, `h` destination, instance nonce, attempt ordinal, and deadline; each operation has a strict typed payload. Pin relay signer in ACP; validate agent signer against the exact stored target and granted instance in relay. Reject unknown fields/operations, stale/future timestamps, wrong host/community/channel, forged results, stale instances, and out-of-order terminal transitions. Capabilities expire after 90 seconds, refreshed every 30 seconds; freshness alone never clears an active lock.
- **Execution claims:** outbox republishes the exact same signed task ID until acknowledged. ACP queues manual work separately from conversation batches, requests an attempt claim immediately before ACP `session/prompt`, and starts only after the relay's durable grant. Grant issuance rechecks permissions, deadline, task state, and total budget under the admission lock; it consumes its ordinal even if the grant or process is lost. Reserve one initial attempt for every unfinished unattempted task. A grant is single-use on a particular runner instance; replay only resends acknowledgment, never execution. A new instance cannot reuse an old grant or infer old work stopped. At most one execution instance owns an attempt.
- **Retries/fallback:** manual work bypasses the channel queue's ten-retry path; all ACP restarts/re-prompts request another grant. Only after confirmed stopping may a retry claim succeed. A qualifying first failure selects the configured Foundry fallback on the second grant even though ordinary failover normally waits for two errors. Two-target profiles cannot retry because both initial attempts reserve the total budget. Ordinary conversations retain their present retry/fallback behavior. An attempt is one supervised ACP execution, not one LLM API call; provider internal tool loops and billing are not separately counted.
- **Scoped manual credential:** the manual child receives an ephemeral key through the existing `BUZZ_PRIVATE_KEY` slot; its public key is registered in the signed attempt claim. The harness retains its agent key for protocol and final-result signing; scrub full agent keys/auth tags from child env and generated MCP configuration. Resolve ephemeral authentication to the stored agent only for authorized reads with the intersection of current agent/channel permissions and this run; reject all delegation-capable Buzz mutations (including messages, mentions, workflow commands, approvals, and agent creation) across HTTP and WebSocket, and revoke at deadline/terminal state. Other external read/tool integrations stay configured; workflows requiring external autonomous delegation are unsupported. This is a control boundary for supervised Buzz execution, not a new sandbox or a guarantee against arbitrary external automation. Child-accessible files must not contain the unscoped Buzz key; unsupported runtime profiles do not advertise capability.
- **Linux credential isolation (Phase 2 implementation clarification):** current UID1000 inheritance is insufficient: the entrypoint exports the full key and persists it in the shared Codex HOME; child env scrubbing does not protect parent `/proc/.../environ`. Use existing `setpriv` to run the harness as UID/GID1001 with only retained `SETUID, SETGID, KILL` capabilities; add `KILL` to the existing Compose startup capability list. Startup root prepares a harness-owned mode0700 key/journal directory with mode0600 files and moves the existing agent identity out of worker HOME without changing identity. Run ordinary ACP children as UID1000, manual ACP children as UID1002, each with separate private HOME/state; apply `setpriv --reuid=<uid> --regid=<gid> --clear-groups --inh-caps=-all --ambient-caps=-all --no-new-privs` to EVERY spawned ACP/helper process before untrusted code, with an explicit sanitized environment. Ordinary children retain their existing required Buzz credential but manual UID1002 cannot read UID1000 process environments/private files; manual children receive only the scoped credential. Grant only the broker socket a dedicated shared group, never share key/journal directories; preserve needed non-Buzz MCP configuration in the separate manual HOME. Validate bind mounts, file modes, inherited FDs, and child configurations for full-key exposure before capability advertisement. Harness retains limited privilege to switch child UIDs and terminate cross-UID process groups; it is not an unprivileged supervisor, although it never runs as root after initialization. Safe Rust launches `setpriv` through `Command`; no `pre_exec`/unsafe or new sandbox package is needed. Native same-user profiles remain unsupported until equivalent isolation is proven. Release-image smoke must assert `setpriv` presence and test both primary and Foundry children: zero effective/permitted/inheritable/ambient capabilities, denied parent/ordinary-child proc memory/environment and identity-file reads, scoped reads succeed, unscoped writes fail. A dummy-data Linux Docker probe already proved the UID/capability and parent-environment/private-file boundary; this is not production-image or malicious-agent sandbox certification.
- **Stop/lifecycle:** run acceptance starts the absolute 20-minute deadline, including queue time. ACP uses a dedicated manual session/process group, records grants and receipts durably before work in a configured persistent state directory, and has a local deadline watchdog independent of relay availability. Deadline sends ACP cancel then terminates/reaps that process group after at most five seconds; initiation of new calls is prohibited at deadline. Relay sweeper revokes credentials and sends cancellation independently. `timed_out` requires signed stopped/reaped evidence; otherwise `stalled` retains all concurrency blocks. Restart reloads the journal and reports unresolved old work; controller/substrate-assisted cleanup must verify old process termination before a trusted runner acknowledgment releases the block. Never recycle locks on lease expiry alone. Cancellation of local execution cannot undo already-issued external effects or guarantee immediate cessation of provider-side billing.
- **Claim-receipt crash recovery (Phase 2 clarification):** a fresh `RecoverClaim` envelope embeds the exact old signed claim and only retrieves its durable receipt, including after expiry or membership revocation. It never allocates execution. A never-granted claim is tombstoned against delayed delivery; a queued supervised task with no live attempt is failed and reconciled so ordinary runs cannot remain queued forever. Existing valid grants and unknown legacy execution retain their stopping requirements. ACP persists recovered grants solely to acknowledge stopping and retries temporary receipt lookup failures without allowing a new launch.
- **Completion:** harness emits final kind `9` with existing result tags, then sends `finished` referencing that stored event and grant; reject missing, wrong-author/channel, or mismatched result references. Failures use fixed safe codes, not provider stderr. Run completes only after dispatch is sealed and all required tasks have signed successful completions; any terminal failure stops remaining new work. Manual-origin results are persisted/displayed normally but excluded from event-triggered automation and automatic agent responses to prevent unbounded follow-on execution. Scheduled results retain ordinary behavior. Outbox and persisted receipts recover crash gaps without replaying completed effects.
- **Reads/UI:** add authorized `GET /workflows?agent_pubkey=<hex>&cursor=...` summary listing, modeled on existing workflow structured GET authentication; enforce exact community owner plus channel visibility, but rows owned by another workflow owner remain disabled. Extend existing `/workflows/{id}/runs` projection with actual state, origin, requester, result link, safe reason, and limits; keep ordinary history read permissions unchanged. Do not expose hidden destination labels or aggregate history. Every summary includes stable binding, schedule/UTC, next occurrence, paused state, last actual result (or unknown), current block reason, quota projection, revision, server time. `46042` is an authorized invalidation signal, followed by a fresh GET; reconnect/focus and 15-second visible-panel polling repair missed events. Query keys include community, identity, agent; cancel/remove them on identity/community changes using existing reset boundaries.
- **Presentation:** insert a Scheduled workflows section in each hosted-agent edit/settings dialog, independent of unsaved name/model edits. Show empty/loading/error separately; keyboard-labelled `Run now <name>`, disabled reason, live queued/running/terminal state, next allowed time and counts. Before activation show inline “Starts fresh and may repeat prior actions. Uses the configured provider and fallback. 20 minutes; two total attempts; 15-minute cooldown; 3/workflow/day, 10/workspace/day; 1 active/agent, 2/workspace. These are execution limits, not a spending cap.” No optimistic success, offline enqueue, or `Run all`; one click signs one event and in-flight double clicks reuse it.

## Risks
- **Read integration parity clarification (Phase 2):** the isolated manual HOME needs its own sanitized MCP configuration. Preserve existing server-enforced project-intelligence and ledger read credentials. Sylars Control currently has only a broad task-submission credential, so add an optional distinct read token in its existing server: allow task/list reads, reject all REST writes and MCP mutation tools before side effects, and mount only that credential/config in manual workers. Ordinary workers retain their existing configuration. This supporting dependency preserves the approved brief data sources without allowing downstream delegation; deploy its read-token support before enabling manual capabilities.
- **Distributed stop uncertainty:** a dead relay, disconnected runner, lost journal, or provider-side request can outlive dispatch. Mitigate with durable grants, local watchdog/process groups, signed stopped evidence and stalled locks; provider billing is never advertised as strictly capped.
- **Scope/compatibility:** two total attempts cannot support arbitrary multi-agent workflows or delegation. The four existing read-only seeded briefs fit the explicit profile; unsupported manual definitions are disabled, full-key-exposing runtime profiles cannot advertise readiness, and ordinary scheduling remains operational. This limitation must be visible at design approval.
- **Partial deployment or stale associations:** current name-only seeds and old runners lack these guarantees. Mitigate with owner-signed pubkey bindings, capability-based fail-closed admission, paired relay/runner immutable promotion, restart/crash tests, and explicit unknown historical outcomes rather than fabricated success.
